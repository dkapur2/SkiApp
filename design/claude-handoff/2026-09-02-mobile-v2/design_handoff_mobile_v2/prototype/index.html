Optional provider

Present only when a key is configured, with incomplete coverage. Absence is shown as unknown.

Lift counts, trail counts, snow report and resort status — ski operations API, its own timestamp, coverage unaudited

Written explanation of a recommendation — language model, constrained to restating validated signals

Illustrative in this prototype

Shown to define the intended experience. None of it is live product behaviour, and none should be read as a claim about conditions.

Condition rating and confidence — needs a versioned deterministic model with documented weights, uncertainty and tests

Surface outlook and best-time index — needs freeze–thaw and rain logic validated against observations

Drive time — needs a routing provider, commercial terms, caching and a straight-line fallback

Nearby, radius and map-viewport results — needs the spatial phase

Radar and nowcast — needs a licensed provider or a public pipeline, tiles, attribution and cost controls

Crowds — no credible source exists; nothing is inferred

Saved mountains, alerts and compare — need persistence, scheduling and stable summary contracts

Rules this design follows

Unknown is never rendered as zero, closed or poor.

Forecasts are labelled separately from observations.

Weather and operations carry their own timestamps.

The main reason for a recommendation is readable without any language model.

A rating is withheld rather than guessed when inputs are missing.

Condition is always carried by a word, never by colour alone.

Long-range days are visibly deemphasised as uncertainty grows.
